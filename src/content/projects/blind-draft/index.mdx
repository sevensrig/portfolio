## What it does

Everyone gets a fake budget and a few empty roster slots. Items from a category (NBA players, celebrities, fast food, or a list you type yourself) are revealed one at a time from a deck nobody has seen, so nobody knows whether something better is coming. Anyone can open the bidding, and when everyone else passes, the top bidder buys it. Every item ends up on someone's roster.

- **Four ways to play:** pass-and-play on one phone, online rooms for 2–4 players with a live lobby, one-on-one against a bot, and a guided tutorial against a scripted coach.
- **Scored, with a winner.** Every pick scores 10–100 points, from hidden tiers that are revealed at the end or, for sports, from real stats blended with outside rankings. Getting a player cheap earns a steal bonus.
- **Online extras:** four emotes during the draft, a chat on the results screen, and rematches with a new category.
- **20 categories**, plus Make Your Own, which works online too.
- **No accounts.** A share button turns the results into an image made to be argued about.

## Real players

Google traffic jumped in October, so I wanted to know whether people actually played. Page views can't tell you that, so I added PostHog to track games started, finished and quit. In its first month (Oct 23 – Nov 24):

- **About 44,000 games:** about 30,000 pass-and-play, 10,400 against the bot and 3,900 online.
- **78% were finished.** Bot games finish 92% of the time and online games 88%.
- **NBA is the most played category**, then Make Your Own, Perfect Life, Celebrities and NFL.

The numbers also shaped what I built. Hosts were sitting alone in rooms and people browsing an empty room list left, so I added a bot to play while you wait. 61% of lonely hosts took it, and when a real player joined mid-game, every host who made a choice picked the real player. When nobody is online, the room list shows a stand-in bot opponent, so the lobby is never empty.

The audience is mostly teenagers, so tracking is deliberately minimal:

- **No cookies, so no consent banner.** PostHog counts visitors with a hash that resets daily.
- **Nothing personal is sent:** no player names, no chat, no custom lists. Room links are scrubbed from every URL, in both keys and values.
- **No session replay or heatmaps**, ever.
- **One tool for errors.** I tried Sentry and removed it the same day. PostHog errors land in the same session as the game events, so a crash reads right next to the quit that followed it.

## How it works

- **One rules engine runs everywhere.** `applyAction(state, action)` is a pure function used by pass-and-play, the bot, the tutorial and online rooms. The server runs a generated copy, and a test fails if that copy drifts from the source. Going from 2 players to 4 meant generalising this one reducer, not forking it, and every existing 2-player test passed unchanged.
- **The bot only sees what a player could.** It's also a pure function of the game state: the current card, the cards already gone, and everyone's wallets and rosters. A test reshuffles the unrevealed cards and checks the bot's move doesn't change. It waits a human-like amount of time before bidding, because a bot that opens 0.3 seconds after a reveal isn't fun to play against.
- **The server owns the deck.** The shuffled deck lives in a table browsers can't read at all. They read a separate table with only the revealed card, bids and rosters. For 3–4 player rooms, the deck is dealt when the host starts, since its size depends on how many players joined. Taking a seat, leaving and starting run in locked Postgres functions, so two players can't grab one seat and nobody can sit down after the deal.
- **Racing moves settle on a version number.** A write only lands if the version still matches. The loser gets the correct state back, so a rejected bid never stays on screen.
- **Moves show up early without trusting anyone.** A bid is announced over the room's realtime channel while the request is in flight. That channel is public to anyone with the room link, so receivers drop anything malformed, from the wrong seat or illegal under the rules, and anything the server doesn't confirm within 4 seconds disappears.
- **The room list uses presence.** A room is listed only while its host is connected, which got rid of ghost rooms with no extra database writes.

## Making online play fast

Online moves took about 780 ms to confirm. I benchmarked full games against production and timed each hop. The server's region wasn't the problem: a move made seven sequential database calls, each costing about 80 ms through Supabase's API gateway, and browsers repeated a CORS check every few seconds. Now a move makes two Postgres calls, one to read and one to write everything in a single transaction. That also fixed a crash between two writes leaving the public state a move behind.

| Full 38-move games in production | Before | After |
|---|---|---|
| Your move confirmed (median) | ~780 ms | 367–425 ms |
| Your move confirmed (90th percentile) | ~935 ms | 525–589 ms |
| Opponent sees your move (median) | ~730 ms | 432–487 ms |
| Opponent sees an announced bid (median) | — | 32–34 ms |

The last row was measured with both seats on one machine, so real network latency between players comes on top.

## What broke

<Callout type="broke" title="Realtime updates, silently denied">
  Online games stopped updating, with no error. My row-level security policy reads a player token from a request header. The REST API sets that header, but Supabase Realtime doesn't, so every change was checked against the policy, denied, and dropped without telling anyone.

  I could have loosened the policy so anyone with a room link could read it. Instead, a database trigger now broadcasts just the new version number, and clients re-fetch the game over REST, where the policy works.
</Callout>

<Callout type="broke" title="A self-serve win button">
  Whoever held the top bid could press "Sell" on their own bid and award themselves the item before anyone else could react. The server had the same hole: its seat check only ran on actions that named a player. The fix lives in the rules engine, and an end-to-end test now sends that request as a hostile client and expects it to be refused.
</Callout>

<Callout type="broke" title="The same players, every game">
  Players noticed the same items coming up again and again. I simulated 20,000 decks: Frank Gore was in every NFL All-Time deck, Jim Brown was in none, and no tight end was ever dealt in NFL Current. The deck builder always drew from the tier with the most cards left. Now every item is equally likely, and a test checks that every player in a pool actually gets dealt. "Random" code still needs a check of how often each item really comes up.
</Callout>

<Callout type="broke" title="A running back at quarterback">
  In an NFL playtest, one player took both quarterbacks, and the other finished the draft with a running back at QB. Locking slots by position had been tried before and killed the bidding tension. Instead, before each reveal the engine now runs a small bipartite matching to check the remaining cards can still fill every open slot, and swaps in a benched player of the same tier if they can't. Placement stayed free; only the deal changed.
</Callout>

<Callout type="broke" title="The load test that kept failing">
  The k6 load test failed 5 times in 4 days, on main and on unrelated branches, always on "illegal moves". Every failure had the same pattern: two racing bids where one player couldn't afford the amount. The script sized both bids from one player's wallet, and the server was right to reject them every time. Each racing bid is now sized to fit both wallets. When a test is flaky, check the test before the system.
</Callout>

## Testing

- **417 unit tests** cover the rules engine and the bot, at 99.8% of lines and 100% of functions. Seeded simulations play 960 full 2-player games and up to 720 games with 3–4 players on every run, from timid to reckless bidding, and check that money is conserved and every item is owned exactly once.
- **69 component tests** run in real Chromium, not a simulated DOM, because the accessibility contrast checks need real rendering.
- **64 end-to-end tests** in Playwright run against the production build, including 20 that play online games across two simulated devices against a real Supabase stack.
- **k6 load tests** run 54 concurrent games against a local stack with no failures and check that exactly one of two racing bids wins.

CI runs all of this as six jobs, so a red X says *what* broke. The last job deploys the database changes, and only from main after everything else passes.
