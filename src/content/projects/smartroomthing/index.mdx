## What it does

The Car Thing was Spotify's discontinued in-car gadget: a small touchscreen with a big dial and four buttons. Mine sits on my desk and controls the room.

- **Turn the dial:** all three speakers get louder or quieter together, keeping their balance.
- **Tap a speaker's fader:** the dial controls just that one for a few seconds.
- **Buttons 1–3:** recall presets (desk, bed, ambient). Press save, then a number, to store the current mix.
- **Button 4:** flips to a now-playing screen with album art and playback controls.
- **Back button:** opens a grid of playlist covers.
- **Previous track:** restarts the song, or goes back a track if you're in the first 5 seconds, like most music players.
- **When nothing is playing:** the screen shows a clock, with Snoopy and Woodstock.

## How it works

The Car Thing has no WiFi and no internet, so everything goes through the Pi.

- **The device** runs a single-page web app (vanilla HTML and JS, no build step) in the kiosk browser it ships with, Chromium 69. The hardware buttons arrive over a local websocket, and the dial arrives as scroll events.
- **A USB tunnel** (`adb reverse`) is the device's only route to the Pi. A watchdog service keeps it alive.
- **A Flask server on the Pi** keeps one persistent connection open to each speaker, with a writer thread per speaker that only ever sends the latest volume. It also proxies every Spotify call, so no secrets ever touch the device.
- **systemd** restarts everything on boot. The screen turns its own backlight off whenever it can't reach the Pi.

## What broke

<Callout type="broke" title="The volume runaway">
  One small volume change took the whole room from 4% to 100% in about 15 seconds, with nobody touching anything. The dial was also changing a laptop's volume in another room.

  I tested each speaker on its own and as a group until the TV stood out. It was signed in to Spotify, so it counted as a Spotify Connect device, and volume changes were echoing back and forth between Cast and Spotify. Two workarounds in code each failed in their own way. The real fix was signing Spotify out of the TV, which cut the feedback loop at its source.

  That fix had a cost: Spotify can only start playback on a device it already knows about. So the playlist grid now tries a list of fallback targets in order, and if none work it asks you to play something first, instead of showing a bare "ERROR".
</Callout>

<Callout type="broke" title="Connections that died silently">
  Sometimes the faders moved and the status endpoint looked healthy, but the speakers ignored every command. Three things hid it: the status read cached volume levels, the writes were asynchronous and always reported success, and the exceptions had empty messages, so the logs said nothing.

  Now every write checks that the socket is really connected and retries once on a fresh connection, and failures show up in the status the UI reads.
</Callout>

<Callout type="broke" title="A tunnel that lies">
  My first attempt to restart the USB tunnel on reconnect (a udev rule) never fired, because the Car Thing shows up as a network adapter, not the device I was matching. Worse, `adb reverse` reports success even after the tunnel is dead. The watchdog now checks the tunnel's health with a real HTTP request through it.
</Callout>

## Making a Pi 2 fast

The Pi 2 has a 900 MHz ARM chip and 1 GB of RAM, and turning the dial felt laggy. Before rewriting anything, I measured: a volume change took 1,177 ms of wall-clock time but only 47 ms of CPU. The server wasn't slow; it was waiting. So a rewrite in a faster language wasn't the answer.

The fixes were about waiting less:
- Reusing connections instead of reopening them.
- Merging a burst of dial clicks into one request (10 clicks became 2 requests).
- Caching album art.
- Replacing a canvas-drawn UI with plain text.

| | Before | After |
|---|---|---|
| Dial → speaker | 1,177 ms | 84 ms |
| Album art | 364 ms | 86 ms |
| Now playing | 394 ms | 225 ms |
| UI render CPU | 5.2% | 0.1% |
| Idle server CPU | ~1.3% | ~0.8% |

## Shipping it

Deploying used to be a list of commands typed over SSH: copy the files, restart the server, unlock the Car Thing's read-only filesystem, push, sync, lock it again. Skip the sync and the next reboot quietly undid the change. The Pi had also drifted from git, running code that was never committed.

Now every pull request runs three checks:

- **36 tests** for the server, with fake speakers and a stubbed Spotify, so they never touch real hardware.
- **Linters set to the Car Thing's Chromium 69.** They fail on features it doesn't have, like optional chaining or flexbox `gap`, which would otherwise break silently on the device.
- **ShellCheck** on the scripts.

Merging to main deploys it. GitHub Actions joins the Pi's private Tailscale network and runs a deploy script that only touches what changed, which takes 3–28 seconds. Then it checks with real requests: the server answers, the files on the Car Thing match, and the Car Thing can reach the server through its USB tunnel. If anything fails, it restores the previous version. I tested this by deploying a deliberately broken commit, and it rolled itself back in 75 seconds.

Access is locked down at every step. No ports are open on my router, and no Tailscale secret is stored: GitHub proves the job's identity directly. CI can reach only SSH on the Pi, and its key can run only one script, which accepts only commits already on main.

| | Before | After |
|---|---|---|
| Deploying | Manual commands over SSH | Merge a pull request |
| A broken deploy | Stays broken until I notice | Rolled back automatically |
| Pi matches git | Drifted | Enforced |

<Callout type="broke" title="The linter's blind spot">
  I tested the browser-compatibility checks by sneaking in features Chromium 69 doesn't support. They caught most of them, but not `aspect-ratio`, because the compatibility data they rely on didn't cover it. I banned it with an explicit rule. A check is only worth trusting once you've watched it fail.
</Callout>

## What I'd do next

Rollback takes 75 seconds because a server that crashes on startup is only noticed when the health check times out. Watching systemd's restart count would catch it in seconds. I've also started a second screen, an HDMI dashboard driven by the same Pi.
